## 幣潮（Coin Cascade）

推幣機。投幣、推板往復、幣堆被推向前緣落下。

規格文件：[`06-minigames/coin-cascade.md`](../../06-minigames/coin-cascade.md)

---

## 為什麼不是吃角子老虎

推幣機天生零決策：投幣、看、拿錢。本作圍繞一條規則重建——**沒掉下去的幣留在台面上，成為之後要被推的地形**。投失的每一枚都在改變棋盤，所以「投在哪」是佈局而不是隨機動作。

---

## 決定性：驗證它比寫它難

整局是 `(種子, 輸入序列)` 的純函數。幣的堆疊碰撞是浮點數密集的，所以作法是固定時間步長、固定解算迭代次數，而且**碰撞依幣的 id 排序解算**而非陣列順序。

自我測試跑 4000 幀混合操作、比對兩次重播的 JSON 是否位元相同。**但「有這條檢查」跟「這條檢查抓得到問題」是兩件事**，所以它被實際破壞驗證過——而過程本身才是重點：

| 注入方式 | 結果 | 原因 |
|---|---|---|
| `Math.random` | 紅了，**但不算數** | 被原始碼掃描擋下，不是重播比對抓到的 |
| `Date.now() % 2` | 沒紅 | 兩次重播落在同一毫秒奇偶，一起偏移 |
| 跨重播計數器交換相鄰幣 | 沒紅 | 交換對解算結果沒有影響，物理沒分歧 |
| **座標擾動 `1e-6`** | **紅了** | `identical seed and inputs must reproduce a bit-identical run` |

**前三次「沒紅」全都是注入無效，不是檢查失效。** 如果在第一次就下結論說「這條檢查是假的」，那會是一個錯誤的指控。

## 量到的數字

全部附 95% 信賴區間——這個 repo 曾因為樣本不足把最難的關卡標成最簡單的，也曾把 8 個種子的雜訊讀成一套機制寫進三份文件。

```
返還率（RTP）      72.51% ± 1.56   （100 場，共投入 22,000 credit）
台面峰值佔用        190.4 ± 1.7 枚  （上限 260）
後期落幣率          2.74 ± 0.10 枚 / 1000 幀
後期停滯的場次      0 / 20          ← 台面不會鎖死
連鎖（≥3 枚）       12.69 ± 0.57 次/場，最長 4.73 ± 0.14 枚
                                    100% 的場次至少一次
近失                135.87 ± 1.19 次/場，100% 的場次都有
```

RTP 72.51% 是這個 repo 第一個**不依賴自製機器人的客觀指標**——它是機台的性質，不是我的模型的性質。守衛是雙邊的：太低是三十秒破產（只有挫折），太高是永遠不會輸（只剩動畫）。

## 瀏覽器實測抓到的死鎖

**症狀**：選著「震動」（3 credit）玩到剩 1 credit，機台就再也結束不了。每次投幣都被拒絕、credit 永遠停在 1、`phase` 永遠不會變成 `ended`——結算畫面出不來，重新開始的按鈕也就不存在。實測數字是**按了 2,425 次、306 秒，credit 卡在 1 動也不動**。

**為什麼所有既有檢查都是綠的**：整局唯一的結束條件是 credit 歸零，而檢查與量測腳本的機器人**全都只投 1 credit 的普通幣**。1 整除 220，所以它必然剛好落在 0——那條「a session terminates」的檢查量到的是機器人的算術，不是機台的性質。重幣與滾珠都是 2，也整除 220；**只有震動的 3 除不盡 220**，而那正是沒有人跑過的組合。

**修法**：買不起的選擇不再被拒絕，而是退回最便宜的幣。最後一枚 credit 永遠買得到東西，於是「會結束」變成引擎的性質，而不是操作者的性質。UI 同步把買不起的選項變灰並取消選取，讓這個退回在按下投幣**之前**就看得到，不是無聲替換。

檢查改成四種選擇全部各跑一輪。把修正拿掉後，紅的正是新加的那一條（前七條照樣通過，不是撞到別的斷言）：

```
AssertionError: a player who leaves 'vibrate' selected never reaches the end of
the run — the machine soft-locks with 1 credit(s) it cannot spend, so the result
screen and the restart button are unreachable
```

修正後同一支瀏覽器腳本：75 秒內結束、`投幣用盡` 結算浮層出現、「再投一輪」通過 `elementFromPoint` 命中測試（318×48，自己是最上層元素）、按下去 credit 回到 220 且浮層關閉。

## 台面不是台面，是一條輸送帶

前一版的 README 把「邊緣投法 RTP 97.73 ± 0.00、中央 78.26」寫成已知缺陷，說根因未知。**那個描述本身是錯的。**

實際去量每一條投法的物理行為，得到的是這個：

| 投點 | RTP | 落幣 x | 台面橫向散佈 |
|---|---|---|---|
| 貼左牆 +0 | 97.73% | 全部 11.0 | **sd 0.00** |
| 左 +22 | 97.73% | 全部 33.0 | **sd 0.00** |
| 左 +40 | 97.73% | 全部 51.0 | **sd 0.00** |
| 正中央 | 97.73% | 全部 210.0 | **sd 0.00** |

**每一條投法都是 97.73%，中央也是。** 跟邊緣、跟側牆完全無關——所以「邊緣支配」從頭到尾就不存在，那是量測腳本在中央投法上混了 12% 特殊幣（半徑不同）才壓低的數字，我把腳本的設定讀成了遊戲的性質。

真正的原因是：**投在同一個 x 的幣，落點的 x 位元完全相同**。兩枚 x 完全相等的幣，分離向量是 `(0, dy)`，接觸法線剛好垂直，於是它們只會沿 y 被推開，**永遠不可能把彼此往旁邊推**。幣堆變成一條剛體柱，台面變成一維輸送帶：投一枚進去、擠一枚出來，220 投回收 209。

這是一個測度為零的巧合，而玩家每一次不動投幣口都會撞到它。把投點擾動 **千分之一單位**，同一局就從 97.73% 掉到 15.68%。

修正是兩個常數：

- `SPAWN_JITTER`——投幣口的鬆動，用 `hash(tick, id)` 產生所以重播仍然位元相同。它只負責打破那個剛好相等，量測顯示 0.10 到 0.40 倍幣半徑之間結果完全一樣，所以它不是一個要調的數字，只要不是零。
- `LATERAL_SLIDE`——接觸分離裡**水平**分量實際套用的比例。原本是 1（完全無摩擦），任何側向推力都無損傳遞，幣堆會攤平成整個台面寬的一層扇形、把推板的力全部往旁邊洩掉，RTP 掉到 ~17%。掃描後取 0.06：

```
slide   左     中央   右     隨機   幣堆 sd
0.00    88.1   90.8   88.1   44.6    1.1   ← 還是一根柱子
0.06    74.6   72.2   75.2   12.3   28.2   ← 取這個
0.12    65.3   57.1   65.5   10.9   38.3
0.24    55.5   41.4   54.6    5.8   49.0
1.00    32.5   12.4   32.5    0.3   75.6   ← 無摩擦，攤平
```

修正後的三條投法：

| | 修正前 | 修正後 |
|---|---|---|
| 左 / 中央 / 右 | 97.7 / 78.3 / 97.7 | **86.6 / 85.0 / 86.4** |
| 邊緣與中央的差 | 19.5pp | **1.6pp** |
| 有連鎖的場次 | 85.7% | **100%** |
| 最長連鎖 | 2.60 枚 | **4.73 枚** |

### 抓得到它的檢查，第一版抓不到

第一版新檢查斷言「幣堆必須有寬度」，用一個種子。把引擎改回原狀跑，**它是綠的**——那個種子的彩池代幣剛好落在投幣線上，把柱子撞散了。是 fixture 運氣好，不是檢查有效，跟上面那個「量到機器人的算術」是同一層錯誤。

改成直接斷言機制本身：**要求同一個 x 的兩枚幣，靜止後 x 不得相同**。這個沒有樣本可以抽，抽不到運氣。改回原引擎後它紅了：

```
AssertionError: 5 of 6 coins asked for the same drop x came to rest at a
bit-identical x — their contact normals are exactly vertical, so they separate
purely along y and can never push each other sideways.
```

## 彩池：也不是缺陷，是量錯了

前一版寫「彩池每場 0.10 次，九成場次看不到」。彩池代幣位置由種子決定、要被推下前緣才爆開——而量測用的機器人**投在固定位置，一次都沒瞄準過它**。

換一個會瞄準的機器人（每次都投在 `triggerZoneX`）：

| 機器人 | 爆開次數/場 | 至少一次的場次 | 彩池 credit | RTP |
|---|---|---|---|---|
| 不理彩池（中央） | 0.57 ± 0.16 | 45.7% | 13.96 ± 3.92 | 75.00 ± 1.81 |
| 追彩池 | **3.00 ± 0.00** | **100%** | **53.95 ± 0.25** | 72.55 ± 1.80 |

機制一直是活的。用一個不做這個決定的機器人去量一個決定，答的是另一個問題。

（追彩池的 ±0.00 這次有結構性解釋，不是飽和：投幣冷卻與代幣從 y=96 走到 y=320 的距離是固定的，所以一個火力全開的追擊者一場能推下幾枚代幣，本來就與種子無關。）

**但這一輪也真的發現一個缺陷**：原設定下追彩池是**免費的**——既爆得到、RTP 又不輸。免費的選項不是決定。於是兩個常數對調成一組槓桿：`TRIGGER_MASS` 決定追它要花多少力氣（原本 1，等於不用力），`POT_CUT_RATE` 決定它回報多少（原本 0.05，整場只餵給彩池 11 credit，比追它的代價還小——那是個**陷阱選項**，跟支配選項是同一個缺陷的反面）。

在 mass=11 掃 cut，看的是「追彩池比不追多賺幾 pp」：

```
cut     0.05   0.10   0.16   0.22   0.30
margin  -7.3   -4.6   -1.4   +1.8   +6.1  pp
```

取 0.16 這個交叉點。兩種玩法的期望回報現在疊在一起（72.55 ± 1.80 對 75.00 ± 1.81，區間重疊），差別只在形狀：追彩池的人有 29% 的分數來自彩池。

### 這條檢查我也寫錯過一次

第一版斷言「追彩池必須比較貴」，用 6 個種子、1pp 的差距。**16 個種子時符號就翻了**，而且換四組各 16 個種子跑，margin 是 −4.9 / −1.0 / +1.4 / +3.8 pp——**它是零附近的雜訊**，對它的符號做任何斷言，都只是在斷言我挑了哪些種子。

平手才是對的結果，所以改成斷言雙邊區間：差距的**絕對值**不得超過 8pp（任一邊支配都紅），加上兩件真正穩定的事——瞄準時每個種子都爆得到，而且彩池佔追擊者分數三成而不是點綴。

## 本地開發

```bash
npm run setup            # 於 repo 根目錄，安裝一次
cd Games/Coin-Cascade
npm run dev              # http://localhost:3000
npm run lint             # tsc --noEmit
npm run check            # 邏輯自我測試（17 項）
npm run balance          # 重現上面所有數字（約 90 秒）
npm run build            # 輸出到 dist/
```

## 備註

以 2D Canvas 繪製，不使用 3D 引擎，**也不使用任何第三方物理函式庫**——碰撞解算自行實作，因為決定性的要求比效能與擬真度都重要。不含任何第三方美術資源。
